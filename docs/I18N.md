# Internationalization (i18n)

The web dashboards (`apps/web/{admin,carrier,client,landing}`) are built on
[next-intl](https://next-intl.dev). Arabic (`ar`) is the primary, right-to-left
locale; English (`en`) and Urdu (`ur`) are also supported. Urdu, like Arabic,
renders right-to-left.

## How a locale is resolved

| App                       | Mechanism            | Where                                   |
| ------------------------- | -------------------- | --------------------------------------- |
| admin / carrier / client  | cookie, no URL prefix | `src/i18n.ts` → `resolveLocale()`      |
| landing                   | URL prefix (`/ar`, `/en`, `/ur`) | `src/middleware.ts` + `src/navigation.ts` |

For the internal dashboards, `resolveLocale()` picks the locale in this order:

1. **The user's explicit choice** — a portal-scoped cookie
   (`naqla-locale-admin` / `-carrier` / `-client`), set by the in-app language
   switcher. This always wins.
2. **The platform default** — the admin-configured `platform.defaultLocale`
   Setting, fetched from the public `GET /settings/platform` endpoint (cached
   ~5 min). This is what a brand-new visitor sees.
3. **`Accept-Language`** header.
4. The app's built-in `DEFAULT_LOCALE`.

### Platform default language

Admins set it in **Admin → Settings → Language** (اللغة). It writes the
`platform.defaultLocale` Setting via `PUT /admin/settings` and is surfaced on
the **public** `GET /settings/platform` response as `defaultLocale` (defaults to
`ar`). Every dashboard reads it through `getPlatformDefaultLocale()` in its
`src/i18n.ts`.

## Messages

Each app keeps its own translations under `apps/web/<app>/messages/<locale>/`,
one JSON file per namespace (`common.json`, `auth.json`, `orders.json`, …). The
set of namespaces differs per app and is wired up in that app's `src/i18n.ts`.
A locale folder must contain **every** namespace file the app imports — a
missing file breaks the build. Untranslated strings are kept as their English
value as a placeholder so nothing is ever missing.

## Adding a new language

Example: adding French (`fr`).

1. **Messages.** For every app, copy the English folder and translate what you
   can; leaving English values in place is fine as a placeholder:
   ```bash
   for app in admin carrier client landing; do
     cp -R apps/web/$app/messages/en apps/web/$app/messages/fr
   done
   ```
   At minimum translate the navigation labels (in `<app>.json`/`landing.json`
   under `nav`), `common.json` (`buttons`, `status`, chrome) and `auth.json`.

2. **Register the code.** Add `'fr'` to `SUPPORTED_LOCALES` in each app's
   `src/i18n.ts`. For **landing**, also add it to `src/navigation.ts` (the
   middleware reads the list from there). If the language is right-to-left, add
   it to `RTL_LOCALES` as well — that single list drives `<html dir>` in every
   layout via `isRtlLocale()`.

3. **Language switcher label.** Add the display name:
   - admin/carrier/client: the `LANGS` array in
     `src/components/language-switcher.tsx`.
   - landing: the `LABELS` map in `src/components/locale-switcher.tsx`.
   - admin default-language picker: `LOCALE_LABELS` in
     `src/app/(app)/settings/page.tsx`, plus `common.json` `languages`.

That's it — dynamic message loading (`import('../messages/${locale}/…')`),
`<html lang/dir>`, and the default-language picker all read from the lists
above, so no other wiring is needed.
