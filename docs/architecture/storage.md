# تخزين الملفات والكائنات (Object Storage)

> المرجع المعتمد لكل ما يخص تخزين الملفات في منصّة نقلة: الشعارات، مستندات
> التحقّق، صور المستخدمين، مرفقات المحادثة، وإثباتات التسليم/الدفع. يحدّد هذا
> المستند البنية والتسمية والآلية ومعايير الأمان وخطة الترحيل إلى Cloudflare R2.

---

## 1. المبادئ الأساسية

1. **مخزّن كائنات متوافق مع S3** هو المصدر الوحيد لكل الملفات (لا تُخزَّن الملفات
   داخل قاعدة البيانات إطلاقًا — قاعدة البيانات تحفظ **مفتاح الكائن `key` فقط**
   كمرجع).
2. **رفع مباشر عبر روابط مُوقّعة (presigned)**: بايتات الملف **لا تمرّ عبر الـ API**
   — العميل/التطبيق يرفع مباشرة إلى المخزّن عبر `presigned PUT`، ويقرأ عبر
   `presigned GET`. هذا يقلّل حِمل الحوسبة والنطاق على السيرفر.
3. **مفتاح الكائن يُبنى في السيرفر** من هوية المستخدم المصادَق + «غرض» محدّد
   (`purpose`) — لا نثق أبدًا بمسار مجلد يرسله العميل.
4. **فصل الحسّاس عن العام**: مستندات التحقّق وصور المستخدمين **خاصّة** (لا تُقرأ
   إلا عبر رابط مُوقّع مؤقّت)، بينما شعارات المنصّة **عامّة** (تُخدَم عبر CDN).
5. **التوافق مع S3** يجعل الانتقال بين MinIO و R2 و AWS S3 مسألة إعدادات
   وموصّل (connector)، دون تغيير منطق التطبيق.

---

## 2. المزوّدون والبيئات

| البيئة | المزوّد | الـ bucket | ملاحظات |
|---|---|---|---|
| **production** | Cloudflare R2 | `nqlah-prod` | متانة عالية + خروج مجاني + CDN |
| **staging** | Cloudflare R2 | `nqlah-staging` | مطابق للإنتاج لاختبار نفس المسار |
| **development** | Cloudflare R2 | `nqlah-dev` | (بديل محلي: MinIO للعمل دون اتصال) |

**معيار إلزامي: bucket مستقل لكل بيئة** (لا مجرّد بادئة مجلد داخل bucket واحد).
السبب:

- **عزل أمني**: لكل bucket **API token خاص** بصلاحيات مقيّدة عليه وحده، فيستحيل
  أن يقرأ أو يحذف تطبيق التطوير ملفات الإنتاج.
- **سياسات مستقلة**: دورة حياة (lifecycle)، نسخ احتياطي، وصلاحيات منفصلة لكل
  بيئة.
- buckets في R2 **مجانية الإنشاء** — فلا تكلفة على الفصل.

يُختار المزوّد وقت الإقلاع عبر المتغيّر `STORAGE_PROVIDER` في
[`StorageModule`](../../apps/api/src/integrations/storage/storage.module.ts)
(`minio` | `r2`)، ويُنفَّذ خلف واجهة
[`StorageConnector`](../../apps/api/src/integrations/storage/storage.connector.ts)
الموحّدة، فبقية التطبيق لا تعرف المزوّد الفعلي.

## 3. بنية المجلدات (prefixes) داخل كل bucket

يُجمَّع التخزين **حسب الكيان + الغرض**، مع فصل العام عن الخاص:

```
branding/                                      ← أصول المنصّة: الشعارات (فاتح/داكن)، صور عامة   [عام]
companies/<companyId>/kyc/<docType>/<obj>      ← مستندات تحقّق المنشأة (CR, VAT, رخصة النقل…)   [خاص]
companies/<companyId>/logo/<obj>               ← شعار المزوّد الخاص (إن وجد)                    [خاص/عام]
users/<userId>/avatar/<obj>                    ← صورة المستخدم الشخصية                          [خاص]
orders/<orderId>/pod/<obj>                     ← إثبات التسليم (ePOD)                           [خاص]
orders/<orderId>/cod/<obj>                     ← إثبات الدفع عند الاستلام                       [خاص]
chat/<orderId>/<messageId>-<obj>               ← مرفقات المحادثة                                [خاص]
```

- **عام (public)**: تحت `branding/` فقط — يُخدَم عبر النطاق العام/CDN دون توقيع.
- **خاص (private)**: كل ما عداه — لا يُقرأ إلا عبر `presigned GET` مؤقّت.
- **التتبّع**: المفتاح نفسه يحمل `companyId`/`userId`/`orderId`، فيمكن سرد كل
  ملفات كيان ببادئة واحدة (`companies/<id>/`)، ومعرفة صاحب الملف من المفتاح فورًا.

## 4. تسمية الكائنات (object key)

الصيغة داخل أي مجلد:

```
<prefix>/<ISO8601-compact>-<uuid8>.<ext>
```

مثال كامل:

```
companies/cmp_abc123/kyc/CR/2026-11-02T0130Z-7f3a9c2e.pdf
└─ من؟           └غرض └نوع └─ وقت (قابل للفرز)   └uuid  └امتداد
```

المعايير:

- **طابع زمني قابل للفرز** (ISO 8601 مضغوط) يعطي ترتيبًا طبيعيًا.
- **uuid قصير** (8 خانات hex) لمنع التصادم.
- **امتداد صحيح** مشتقّ من نوع المحتوى.
- **قاعدة البيانات هي المرجع الرسمي**: لكل ملف صفّ (`KYCDocument` / رسالة /
  `Setting`) يحمل `key + uploaderId + companyId + type + createdAt`. المفتاح
  «مرآة» بشرية تسهّل التصفّح اليدوي، والربط الموثوق عبر قاعدة البيانات.

### ⚠️ الخصوصية في المفاتيح

- **معرّفات مبهمة فقط** في المفتاح (`companyId`/`userId` من نوع cuid مبهم).
- **يُمنع منعًا باتًّا** وضع اسم شخص أو رقم هوية أو أي بيانات شخصية في اسم الملف
  (المفاتيح قد تظهر في السجلّات والروابط).
- **سهولة النسيان/الحذف**: حذف بيانات مستخدم = حذف ببادئة واحدة
  (`delete users/<id>/*` أو `companies/<id>/*`).

## 5. بناء المفتاح في السيرفر: الـ `purpose`

نقطة أمان جوهرية: **العميل لا يرسل مسار المجلد**. بدلًا من ذلك يرسل **غرضًا
محدّدًا** (`purpose`) من قائمة مغلقة، والسيرفر يركّب البادئة من هوية المستخدم
المصادَق + الغرض.

| `purpose` | البادئة المبنية في السيرفر | الوصول | من يرفع |
|---|---|---|---|
| `kyc` | `companies/<actor.companyId>/kyc/<docType>/` | خاص | المنشأة |
| `companyLogo` | `companies/<actor.companyId>/logo/` | خاص/عام | المنشأة |
| `avatar` | `users/<actor.userId>/avatar/` | خاص | المستخدم |
| `pod` | `orders/<orderId>/pod/` | خاص | السائق (للطلب المكلّف به) |
| `cod` | `orders/<orderId>/cod/` | خاص | السائق |
| `chat` | `chat/<orderId>/` | خاص | أطراف الطلب |
| `branding` | `branding/` | عام | الأدمن فقط |

القواعد:
- يتحقّق السيرفر أن المستخدم يملك حق الرفع للكيان المعني (مثلاً `orderId` يخصّ
  طلبًا هو طرف فيه، و`branding` للأدمن حصريًا).
- أي `purpose` غير معروف يُرفَض.
- هذا يمنع كتابة عميل في مسار كيان آخر أو مجلد خاطئ.

## 6. آلية الرفع والقراءة

### الرفع (مباشر إلى المخزّن)
```
1) العميل → POST /uploads/presign { purpose, docType?, orderId?, filename, contentType, sizeBytes }
2) السيرفر: يتحقّق من الصلاحية، يبني الـ key، يعيد { uploadUrl (presigned PUT), key }
3) العميل → PUT <uploadUrl> (بايتات الملف مباشرة إلى المخزّن، بدون المرور بالـ API)
4) العميل → يحفظ الـ key على المورد (مستند/رسالة/إعداد) عبر الـ API المناسب
```

### القراءة
- **خاص**: `presigned GET` مؤقّت (صلاحية قصيرة، مثلاً ساعة) يُطلب عند الحاجة.
- **عام** (`branding/`): رابط ثابت عبر النطاق العام/CDN.

### توقيع الروابط على المضيف العام (مهم)
الروابط المُوقّعة تُسلَّم لجهاز (هاتف/متصفّح) لا يصل للمضيف الداخلي. لذلك:

- **MinIO**: تُوقَّع على `MINIO_PUBLIC_URL` (نطاق عام خلف بروكسي يحافظ على الـ Host
  ويمرّر المسار كاملًا) — راجع الإصلاح في
  [`minio-storage.connector.ts`](../../apps/api/src/integrations/storage/minio-storage.connector.ts).
- **R2**: نقطة الـ S3 (`<account>.r2.cloudflarestorage.com`) **عامة أصلًا عبر
  HTTPS**، فالروابط المُوقّعة تعمل من الجهاز مباشرة دون بروكسي.

---

## 7. الوصول والخصوصية والاحتفاظ

- **خاص افتراضيًا**: كل المجلدات خاصّة عدا `branding/`.
- **روابط مؤقّتة**: صلاحية `presigned GET` قصيرة (الافتراضي ساعة) وصلاحية الرفع
  أقصر (5 دقائق).
- **حدود الرفع**: 25MB كحدّ أقصى، وأنواع MIME مسموح بها فقط (صور، فيديو، صوت،
  PDF/Word/Excel/نص) — تُفرَض في
  [`uploads.controller.ts`](../../apps/api/src/modules/uploads/uploads.controller.ts).
- **الاحتفاظ/النسيان**: الحذف ببادئة الكيان يحذف كل ملفاته دفعة واحدة.
- **بيانات حسّاسة قانونيًا**: مستندات التحقّق (هوية، سجل تجاري) — تبقى خاصّة ولا
  تُشارك، وتُراجَع عبر `PUT /companies/:id/kyc/:docId/status` من الأدمن.

---

## 8. الخدمة العامة والـ CDN (الشعارات)

- شعارات المنصّة تحت `branding/` وتُخدَم عبر **نطاق مخصّص** مربوط بالـ bucket
  (`storage.nqlah.nx.sa`) خلف **CDN كلاودفلير**، مع ترويسات كاش طويلة
  (`Cache-Control: public, max-age=31536000, immutable` — يُدعم ذلك باسم ملف
  جديد عند كل تغيير شعار، busting تلقائي).
- **شعار افتراضي مُضمَّن** في التطبيق والويب (fallback) لأول تحميل أو عند انقطاع
  الاتصال.
- السبب في عدم تخزين الشعارات على السيرفر مباشرة: الأدمن يغيّرها ديناميكيًا
  (راجع سجل الشعار القابل للتهيئة)، ونريد كاش CDN + متانة + اتساق مع بقية الأصول.

## 9. متغيّرات البيئة

### R2 (البيئات الثلاث)
```bash
STORAGE_PROVIDER=r2
R2_ENDPOINT=https://<account-id>.r2.cloudflarestorage.com  # نقطة S3 العامة
R2_ACCESS_KEY=<r2-access-key>              # token مقيّد على bucket البيئة
R2_SECRET_KEY=<r2-secret>
R2_BUCKET=nqlah-prod                       # أو nqlah-staging / nqlah-dev
R2_REGION=auto                             # R2 يتجاهل المنطقة؛ الموقّع يحتاجها
R2_PUBLIC_URL=https://storage.nqlah.nx.sa  # النطاق العام لأصول branding
```
> يمكن ضبط هذه القيم أيضًا من **مركز التكامل (Integration Hub)** في لوحة الأدمن
> (التخزين → Cloudflare R2) بدل متغيّرات البيئة.

### MinIO (التطوير المحلي البديل)
```bash
STORAGE_PROVIDER=minio
MINIO_ENDPOINT=localhost
MINIO_PORT=9000
MINIO_USE_SSL=false
MINIO_ROOT_USER=minioadmin
MINIO_ROOT_PASSWORD=minioadmin
MINIO_BUCKET=nqlah-dev
MINIO_PUBLIC_URL=http://localhost:9000
```

> ملاحظة اتساق: يجب أن يتطابق مضيف `*_PUBLIC_URL` مع المضيف الذي يُنهي TLS
> فعليًا ومع `NEXT_PUBLIC_MINIO_URL` في الويب.

## 10. خطة الترحيل من MinIO إلى R2

1. **إنشاء الموارد**: 3 buckets في R2 (`nqlah-dev/staging/prod`) + API token
   مقيّد لكل bucket، وربط نطاق عام (`storage.nqlah.nx.sa`) ببكت الإنتاج لأصول
   `branding/`.
2. **نسخ الملفات الحالية**: من MinIO إلى R2 بأداة متوافقة مع S3
   (`rclone` أو `aws s3 sync` مع نقطتي نهاية) — حفاظًا على المفاتيح كما هي.
3. **تبديل الإعدادات**: ضبط `STORAGE_PROVIDER=r2` + متغيّرات R2 في كل بيئة،
   ثم إعادة النشر.
4. **تحقّق**: رفع/قراءة تجريبي لكل غرض (kyc/avatar/chat/branding) من جهاز حقيقي.
5. **تراجع (rollback)**: الإبقاء على MinIO وبياناته حتى التأكّد، فالعودة = تبديل
   `STORAGE_PROVIDER` عكسيًا.

---

## 11. النسخ الاحتياطي والمتانة

- **R2**: متانة عالية مُدارة (نسخ متعدّدة) — ومع ذلك يُفضّل تفعيل **versioning**
  على bucket الإنتاج، ولقطة دورية (snapshot) للبيانات الحسّاسة.
- **MinIO (محلي)**: نسخة واحدة على القرص — نسخ احتياطي يدوي دوري للـ volume إن
  استُخدم لأي بيئة حيّة.
